# AI Pet-SMM Analytics

Креативная аналитика Instagram-рилсов пет-блога: метрики своих роликов и
конкурентов, разметка атрибутами, а дальше — контент-планы и подбор рекламных
интеграций.

**Спринт 1 (готово):** фундамент, база данных, базовый дашборд.
**Спринт 2 (готово):** синхронизация с Instagram Graph API, график динамики,
топ-3 по engagement rate.

**Почему всё устроено именно так** — в [docs/WORKLOG.md](docs/WORKLOG.md):
журнал решений по спринтам с обоснованиями и список открытых вопросов.

## Запуск

```bash
npm install
cp .env.example .env.local   # заполнить значениями из Supabase Dashboard

npm run db:push              # применить схему к базе
npm run db:check             # убедиться, что всё на месте
npm run dev                  # http://localhost:3000
```

`db:push` применяет `supabase-schema.sql` через psql. Если psql не установлен —
то же самое руками: Supabase Dashboard → SQL Editor → New query → вставить файл
целиком → Run. Скрипт идемпотентный, повторный прогон ничего не ломает.

`db:check` ходит в базу тем же anon-ключом, что и приложение, и проверяет
таблицы, стартовые теги, запись и generated-колонку. То есть проверяет ровно
тот путь, по которому пойдёт дашборд.

**Если `db:push` не может подключиться:** прямое подключение
`db.<ref>.supabase.co` у Supabase работает только по IPv6. Если у провайдера
его нет, возьмите строку Session pooler в Dashboard → Connect — она по IPv4.

## Структура

```
app/
  actions/              server actions: ручное добавление и синхронизация
  page.tsx              дашборд: сводка, график, топ-3, таблица
  reels/[id]/page.tsx   карточка видео: статистика и теги
  error.tsx             граница ошибок (частый случай — пустой .env.local)
  not-found.tsx         404
components/
  ui/                   примитивы shadcn/ui
  reels/                компоненты предметной области
  dashboard/            график, топ-3, кнопка синхронизации
hooks/                  клиентские хуки
lib/
  analytics.ts          производные показатели: ER, ряд для графика, топ
  instagram/            клиент Graph API: типы, схемы, лестница метрик
  queries/              чтение данных для серверных компонентов
  supabase/             клиенты: client.ts (браузер), server.ts (сервер)
  validations/          схемы Zod, общие для формы и экшена
types/database.ts       типы схемы Supabase
supabase-schema.sql     DDL + GRANT + RLS + стартовые теги
scripts/                db:push и db:check
```

Две вещи, которые стоит знать про эту раскладку:

**Чтение и запись разведены.** `lib/queries` вызывается из серверных
компонентов, `lib/actions` — из форм. У них разные правила: запросы просто
рендерятся, мутации валидируют вход и инвалидируют кеш через `revalidatePath`.

**Клиент Supabase не один, а два.** В ТЗ значился единый `lib/supabase.ts`, но
в App Router это ловушка: серверный клиент импортирует `next/headers`, и один
общий модуль либо утащит серверный код в браузерный бандл, либо сломает сборку.
Поэтому `lib/supabase/client.ts` (браузер) и `lib/supabase/server.ts` (сервер,
с `import "server-only"` как страховкой) живут отдельно.

## Синхронизация с Instagram

Кнопка «Синхронизировать статистику» на дашборде тянет последние рилсы через
Graph API и обновляет таблицу `reels`. Видео сопоставляются по ссылке: если
запись уже есть — обновляются метрики, если нет — создаётся новая с `type = 'my'`.
Ссылки с обеих сторон прогоняются через нормализацию, поэтому видео, заведённое
руками, не задвоится после первой же синхронизации.

Без `INSTAGRAM_ACCOUNT_ID` и `META_ACCESS_TOKEN` кнопка остаётся неактивной, а
всё остальное работает как раньше.

**Про имена метрик.** Meta регулярно переименовывает метрики Insights: счётчик
проигрываний по очереди звался `video_views`, `plays`, затем `views`. Какая
версия API отвечает вашему токену — заранее неизвестно, поэтому клиент пробует
наборы метрик по очереди и берёт первый, который API принял
(`lib/instagram/client.ts`, константа `METRIC_LADDER`). Проверено на заглушках,
имитирующих обе версии API.

**Что осталось хрупким.** Ссылки на обложки, которые отдаёт Graph API,
подписаны и через несколько дней начинают отдавать 403. Пока мы просто
откатываемся на заглушку вместо битой картинки; складывать обложки в Supabase
Storage — задача Спринта 3.

## Безопасность: прочитать до деплоя

`NEXT_PUBLIC_SUPABASE_ANON_KEY` попадает в браузерный бандл — так задумано
Supabase. Защищает данные не секретность ключа, а RLS.

Сейчас в `supabase-schema.sql` действует раздел **6a — dev-политики**, которые
разрешают анонимному ключу всё. Для локальной разработки это удобно, для
публичного деплоя означает, что любой посетитель может читать и удалять вашу
базу. Перед выкладкой удалите блок 6a и раскомментируйте 6b (чтение всем,
запись — только авторизованным).
