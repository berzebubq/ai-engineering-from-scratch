## Что это за проект

AI SMM-помощник для креативной аналитики пет-блога в Instagram. Собирает
метрики по своим видео и видео конкурентов, размечает их атрибутами
(в перспективе — автоматически, через Vision API и Whisper) и помогает
с контент-планами и рекламными интеграциями.

Роли: заказчик выступает продакт-менеджером и принимает продуктовые решения,
Claude — разработчиком. Работа идёт итерациями-спринтами.

## Решения

### 1. Приложение живёт в `projects/`, а не в корне репозитория

**Спринт 1.** В ТЗ было «в текущей директории», но корень занят: это публичный
форк учебного курса с `README`, `phases/`, `site/` и `vercel.json`, который
деплоит статичный сайт курса. Next.js в корне подмешал бы `package.json` и
`node_modules` к материалам курса и начал драться за один конфиг деплоя.

Решение принято продактом из трёх вариантов. Следствие: **в Vercel нужно
указать Root Directory = `projects/ai-smm-analytics`.**

Отдельно стоит помнить: форк чужого курса — плохой долгосрочный дом для
продукта, однажды `git pull upstream` притащит 260 уроков в вашу историю.
Вынести в свой репозиторий — открытый вопрос.

### 2. Клиент Supabase разделён на два файла

**Спринт 1.** В ТЗ значился единый `lib/supabase.ts`. В App Router это ловушка:
серверный клиент импортирует `next/headers`, и общий модуль либо утащил бы
серверный код в браузерный бандл, либо сломал сборку.

Итог: `lib/supabase/client.ts` (браузер) и `lib/supabase/server.ts` (сервер, под
`import "server-only"` как страховкой). Серверный клиент создаётся заново на
каждый запрос — в куках лежит сессия конкретного пользователя, общий клиент
раздал бы её всем.

### 3. Чтение и запись разведены по разным папкам

`lib/queries/` зовётся из серверных компонентов, `app/actions/` — из форм.
У них разные правила: запросы просто рендерятся, мутации валидируют вход и
инвалидируют кеш через `revalidatePath`.

В Спринте 1 экшены лежали в `lib/actions/`; в Спринте 2 продакт попросил
`app/actions/`, папка переехала целиком ради единообразия. Папка внутри `app/`
без `page.tsx` маршрута не создаёт — это безопасно.

### 4. shadcn/ui написан руками, а не поставлен CLI

**Спринт 1.** `ui.shadcn.com` заблокирован сетевой политикой окружения (403 на
CONNECT), CLI не смог скачать реестр. Исходники компонентов положены в
`components/ui/` вручную — shadcn/ui по своей природе copy-paste исходники, а не
рантайм-зависимость, так что результат идентичен. Зависимости (Radix, CVA,
tailwind-merge) поставлены с npm, который доступен.

### 5. Формула Engagement Rate менялась — и это важно

**Спринт 1:** `(лайки + сохранения + комментарии + репосты) / охват`.
**Спринт 2:** продакт зафиксировал `(лайки + сохранения) / охват`.

Две разные формулы под одним названием в одном приложении — это баг, поэтому
в Спринте 2 база приведена к продуктовой спецификации, а не оставлена как была.
**Цифры ER, которые вы видели после Спринта 1, изменились.**

Формула живёт в двух местах и они обязаны совпадать: generated-колонка
`reels.engagement_rate` в `supabase-schema.sql` и функция `engagementRate()`
в `lib/analytics.ts`. Храним долей, проценты — дело отображения.

Тип колонки — `numeric` без указания точности намеренно: `numeric(6,4)`
переполнился бы на вирусном ролике с крошечным охватом (проверено, ER доходил
до 1000000).

### 6. Ключ upsert — ссылка, а не Instagram ID

**Спринт 2.** Синхронизация могла бы сопоставлять видео по `instagram_id`, но
тогда ролик, заведённый руками (у него `instagram_id` пустой), при первой же
синхронизации задвоился бы или упёрся в уникальность `url`.

Поэтому upsert идёт по `url`, а `instagram_id` хранится **без уникального
ограничения** — только с обычным индексом. Ссылка есть у записей обоих
происхождений, и синхронизация подхватывает ручные, а не плодит дубли.

Чтобы это работало, обе стороны прогоняют ссылку через `normalizeReelUrl()`
(`lib/instagram/url.ts`): иначе `.../reel/ABC/?igsh=...` из Graph API и
`.../reel/ABC/`, введённое руками, стали бы двумя разными строками.

Цена решения: если Instagram когда-нибудь поменяет permalink у существующего
видео, появится дубль. Маловероятно, ловится глазами.

### 7. Имена метрик Graph API перебираются лестницей

**Спринт 2, самое хрупкое место.** Meta регулярно переименовывает метрики
Instagram Insights: счётчик проигрываний по очереди звался `video_views`,
`plays`, затем `views`. Какая версия отвечает вашему токену — зависит от
настроек приложения в Meta.

Сверить с документацией не удалось: домены Meta заблокированы сетевой политикой
окружения. Поэтому вместо жёсткого имени клиент идёт по лестнице наборов метрик
(`METRIC_LADDER` в `lib/instagram/client.ts`) и берёт первый набор, который API
принял, а любую метрику «проигрываний» кладёт в колонку `plays`.

Проверено на заглушках, имитирующих обе версии API: когда `views` отклоняется,
клиент спускается на `plays` и получает те же данные.

Если Meta придумает новое имя — добавьте ступень в `METRIC_LADDER`, больше
менять ничего не нужно.

### 8. Лайки и комментарии берутся не из insights

Поля `like_count` и `comments_count` приходят прямо с медиа-объекта и стабильны
между версиями API, в отличие от insights. Из insights берём только `reach`,
`saved`, `shares` и проигрывания.

### 9. Провал одного видео не роняет синхронизацию

У свежих публикаций и у роликов, опубликованных до перехода на бизнес-аккаунт,
статистики может не быть вовсе (Meta отвечает кодом 100 с подкодом 2108006).
Такое видео отмечается отдельно, синхронизация продолжается, статус становится
`partial`. Лучше обновить девять из десяти, чем ни одного.

Ошибки, которые сменой набора метрик не лечатся (истёкший токен, нехватка прав,
лимит частоты, отсутствие статистики), обрывают лестницу сразу — незачем тратить
квоту запросов.

### 10. RLS: сейчас открыто всё, и это временно

`supabase-schema.sql`, раздел **6a**, помечен `DEV ONLY`: анонимный ключ может
читать, писать и удалять.

Так и задумано для локальной разработки, но `NEXT_PUBLIC_SUPABASE_ANON_KEY` по
устройству Supabase вшивается в браузерный бандл и виден любому посетителю.
Защищает данные не секретность ключа, а RLS. **Пока действует 6a,
задеплоенное приложение = публичная база.**

Готовый production-вариант лежит рядом закомментированным (раздел **6b**):
читать всем, писать только авторизованным. Оба блока прогнаны на живом
PostgreSQL под ролями `anon` и `authenticated` — работают как заявлено.

Важное следствие: после переключения на 6b форма «Добавить видео» перестанет
работать, пока в приложении нет авторизации. Авторизацию логично делать
отдельной задачей перед первым деплоем.

### 11. Права на таблицы выданы явно

Изначально схема полагалась на default privileges Supabase, которые сами выдают
`anon` и `authenticated` доступ к новым таблицам. На стоковом проекте это
работает, в других случаях даёт `permission denied for table reels` без внятной
причины. Локальный прогон это вскрыл, и появился раздел **5b** с явными `GRANT`.
Повторный грант ничего не стоит, неявная зависимость — стоит.

### 12. Ссылка валидируется как `instagram.com`

Осознанное ограничение: инструмент про Instagram, и опечатка должна ловиться на
вводе, а не всплывать через месяц пустой аналитикой. Разрешённые хосты — массив
`ALLOWED_HOSTS` в `lib/validations/reel.ts`. Понадобится TikTok или YouTube
Shorts — допишите хост, остальное менять не нужно.

### 13. График: прямые отрезки, одна серия, подпись на пике

**Спринт 2.** `type="linear"`, а не `monotone`: сглаживание пририсовало бы между
точками плавные подъёмы и провалы, которых в данных нет. Каждая точка —
измеренная сумма проигрываний за сутки.

Серия одна, поэтому легенды нет (её заменяет заголовок карточки), а цвет взят
один — слот 1 валидированной палитры (`--viz-series-1` в `app/globals.css`,
`#2a78d6` в светлой теме и `#3987e5` в тёмной). Значения проверены на контраст к
поверхности и различимость при нарушениях цветовосприятия в обеих темах.

Подпись значения ровно одна — на пиковой точке. Цифра у каждой точки
превращается в шум, который перестают читать.

### 14. Обложки протухают

Ссылки на превью, которые отдаёт Graph API, подписаны и через несколько дней
начинают отдавать 403. Синхронизация это вскрыла сразу: битая картинка
расползалась alt-текстом по таблице.

Сейчас `ReelThumbnail` ловит `onError` и откатывается на заглушку. Настоящее
решение — складывать обложки в Supabase Storage, это следующий спринт.

### 15. Заделы в схеме, заложенные заранее

Приняты продактом в Спринте 1 («минимум + пара заделов»), чтобы не писать
миграции в следующих спринтах:

- `reels`: `thumbnail_url`, `caption`, `comments`, `shares`, `published_at`,
  `updated_at`
- `reel_tags`: `source` (`manual` / `vision` / `whisper` / `llm`) и
  `confidence` — под авторазметку
- `reels.instagram_id` — понадобится, чтобы скачивать видео для Whisper и Vision

## Ограничения окружения разработки

Claude работает в облачном контейнере с сетевой политикой, которая закрывает
почти всё. Это влияло на решения и на то, как всё проверялось.

**Закрыто:** `supabase.co`, `supabase.com`, домены Meta (`graph.facebook.com`,
`developers.facebook.com`), `ui.shadcn.com`, релизы GitHub.
**Открыто:** npm-реестр, Google Fonts, git-операции с GitHub.

Отсюда два следствия. Первое: применить схему к вашей базе и проверить живой
Graph API из этого окружения нельзя — это делаете вы у себя. Второе: проверка
велась на локальных подменах.

Как проверялся Спринт 2: поднимался настоящий **PostgreSQL 16** с реальной
схемой, поверх него — шим PostgREST (сам PostgREST скачать не дали), плюс
заглушка Graph API, умеющая изображать обе версии API. Дальше — прогон
в Chromium через Playwright: 16 проверок, включая откат по лестнице метрик,
отсев фото от рилсов, нормализацию ссылки, повторную синхронизацию без дублей,
порядок топ-3 и вёрстку на 390px.

Миграция Спринта 2 проверялась именно вашим сценарием: разворачивалась схема
Спринта 1, наливалась строка, применялась новая схема — данные целы, ER
пересчитался с 0.2 на 0.1, повторный прогон ничего не трогает.
